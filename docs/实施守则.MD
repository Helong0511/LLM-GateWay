# 实施守则（执行纪律与红线）

> 配套文件：《软件需求.MD》v3.0（需求总纲）、《实施步骤.MD》（执行步骤）。
> 本守则是**执行层面的强制纪律**。任何实施者（人或 AI）在动手前必须通读；守则与需求文档冲突时，以需求文档为准并在 ADR 中记录差异。
> 每次开工先做三件事：读本文 → 读 `docs/IMPLEMENTATION_PROGRESS.md`（当前进度）→ 读当前阶段的 DoD。

## 一、六条铁律（违反即返工，无例外）

1. **真实实现，禁止造假**。不允许静态假页面、假数据、假装成功的按钮、伪造的测试结果、伪造的链上/支付验证结论。未接通的功能必须显式标注"未启用"。演示数据必须带明确标记。
2. **资金正确性高于一切**。任何涉及余额、账本、订单、退款的代码，必须先满足账本不变量（需求 §8.2）与幂等要求，再谈功能完成。资金代码没有"先跑通再补事务"这种说法。
3. **凭证隔离**。五类凭证（平台管理密钥、上游密钥、网关虚拟 Key、用户 API Key、用户会话）不得混用、不得互转、不得出现在前端响应、日志、Git、截图中。生产密钥不写入任何入库文件。
4. **不可逆操作必须暂停请示**：真实支付、真实链上转账、删除/覆盖用户数据、更换加密主密钥、生产环境结构迁移。停下来说明风险与回退方案，等明确指令。
5. **不跳阶段**。严格按《实施步骤.MD》阶段顺序执行；每阶段 DoD 全绿才可进入下一阶段。发现前序阶段缺陷，先修再走。
6. **测试必须真实运行**。"写了测试文件"不算完成，"测试在当前环境实际执行并通过"才算。无法执行的环境（缺真实凭证）必须明示跳过原因，禁止标记为通过。

## 二、工程纪律

### 2.1 每次任务的标准动作

1. 明确任务对应的需求章节号与测试用例号（TC-*）。
2. 先检查现状：该功能是否已存在？存在则评估"保留/修复/重构/替换"，结论记 ADR。
3. 写代码 + 写测试（同一批交付，禁止"代码先合、测试后补"）。
4. 本地跑通：`make lint && make test`（或等价命令）。
5. 更新 `docs/IMPLEMENTATION_PROGRESS.md`：做了什么、证据（测试输出摘要）、遗留风险。
6. 非显而易见的技术决策写 ADR（docs/adr/，模板见需求附录 C）。

### 2.2 代码质量底线

- Python：Ruff 零告警；mypy 对 billing/payments/security/rbac 四个模块 strict 通过；函数不依赖隐式全局状态；时钟可注入。
- TypeScript：strict 模式；API 类型只从 openapi-typescript 生成，不手写请求/响应类型。
- SQL：只走 SQLAlchemy/Alembic，禁止字符串拼 SQL；迁移文件必须可 upgrade 且资金相关迁移可回滚或有补偿迁移。
- 提交：原子提交，提交信息说明"为什么"；不把无关改动混进一个提交。
- 依赖：新增依赖必须有理由（记录到进度文档）；锁定版本；CI 跑 pip-audit / npm audit。

### 2.3 禁止事项（工程）

- 禁止覆盖用户已有数据、配置、数据库；迁移只做增量。
- 禁止在 router 里写业务规则/直接操作事务（分层见需求 §3.2）。
- 禁止用浮点数表示金额；金额一律 NUMERIC/Decimal，序列化为字符串。
- 禁止在 router/前端信任客户端传入的用户 ID、金额、支付成功标志——一切归属与金额以服务端会话/查单为准。
- 禁止"先默认放行、后续再加权限"：新接口默认拒绝，按需开放。
- 禁止 TODO/空文件占位冒充完成（需求 §17 已明令）。

## 三、安全纪律

1. 新写任何接口前先回答三个问题：谁可以调？能调谁的资源？失败时返回什么（不泄露内部）？
2. 日志必过脱敏过滤器（密码、Bearer、sk- 密钥、Cookie、邮箱打码、私钥/助记词模式）；新增敏感字段类型时必须同步更新脱敏规则。
3. 密钥处理：上游密钥只进 LiteLLM/Secret Manager；用户 API Key 只存摘要、创建时只展示一次；加密主密钥只从环境变量注入。
4. SSRF 白名单校验（需求 §6.1 五条）是供应商 URL 入库的前置条件，不可裁剪。
5. 管理操作：服务端 RBAC 校验 + 审计日志（哈希链）+ 高风险二次验证，三者齐备才算完成。
6. 每完成一个安全相关模块，立刻写对应负向测试（越权、伪造、重放、篡改），编号 TC-SEC-*。

## 四、资金纪律

1. 账本只增不改；纠错用反向流水；退款必须引用原订单。
2. 扣费路径只有一条：预扣（hold）→ 提交（commit）/ 释放（release）。任何新增扣费场景必须复用该路径，不得另造扣款逻辑。
3. 幂等键先行：所有资金写操作先定义幂等键（格式 `{type}:{biz_id}`），再写代码。
4. 并发安全用数据库手段（行锁/条件更新），不信应用层记忆、不信 Redis 存财务状态。
5. USDT 入账三重验证（验签 + IP 白名单 + 主动查单）缺一不可；确认数不达档不入账；回调与轮询并发只入账一次。
6. 每次涉及资金的代码变更，必须重跑 TC-BILL-*、TC-PAY-*、TC-CONC-* 全量。

## 五、文档纪律

| 文档 | 更新时机 |
| --- | --- |
| IMPLEMENTATION_PROGRESS.md | 每次任务结束必更新 |
| docs/adr/ | 每个非显然决策 |
| TEST_PLAN.md | 新增用例时同步 |
| API_SPECIFICATION.md | 接口变更同 PR 更新 |
| RUNBOOK.md | 遇到并解决新故障后补录 |
| DEPLOYMENT.md | 部署流程任何变化时 |

文档与代码不一致时，以代码事实为准修文档，并追查为什么会不一致。

## 六、升级与请示规则

**立即暂停并请示**（不可自行决定）：
- 接入真实支付渠道、真实 USDT 网关并收发真实资金；
- 使用真实上游付费 Key 跑 live 测试；
- 生产数据的删除、覆盖、批量修改；
- 加密主密钥更换、已签发凭证的批量轮换；
- 需求文档中标记"涉及不可逆操作"的任何条目。

**自行决定但记录 ADR**：目录结构、命名、默认值、库内小版本选择、UI 细节。

**不请示也不记录 = 违规。**

## 七、AI 实施者特别条款

1. 每次会话开工先读：本守则 → 进度文档 → 当前阶段任务；不清楚现状时不许写代码。
2. 修改文件前先读该文件；不凭空假设已有代码内容。
3. 工具调用失败两次以上，停下来分析根因换方案，不机械重试。
4. 报告状态用事实语言："已执行 X，结果 Y（证据 Z）"；禁止"应该可以了"。
5. 上下文不足时主动收缩任务粒度（一次一个小模块），保证每一步可验证。
