## 一、项目目标与范围边界

### 1.1 项目目标

你是一名资深全栈架构师、AI Gateway 工程师、支付与计费系统工程师、数据库工程师、DevSecOps 工程师和 UI/UX 设计师。

请在当前工作区内，完整设计、开发、测试、修复并完善一个可以真实运行和部署的 AI 算力中转站平台。

项目定位：

- 面向个人开发者、企业客户和 AI 应用开发团队。
- 聚合多个合法、授权的大模型 API 服务商。
- 统一接入不同厂商的模型。
- 提供统一 API 接口、API Key、模型选择、用量统计、计费和管理。
- 支持后续扩展本地模型、自有 GPU 推理服务及多个算力节点。
- 支持多用户、多供应商、多模型、多密钥和多种计费规则。
- 前端既要有专业的商业展示网站，也要有完整的用户控制台和运营管理后台。
- 所有关键业务必须真正连接数据库、后台 API 和模型中转服务，禁止只做静态页面、假数据或仅能演示的按钮。
- 【v3.0】运营模式支持二选一并在系统配置中显式声明：**大陆模式**（ICP 备案、微信/支付宝、CNY 结算）或**海外模式**（免备案、Stripe + USDT 收款、USD 结算）。两种模式的合规义务见第十九章，**禁止混用**（海外模式不得向中国大陆居民提供加密货币相关服务）。

请优先实现安全、正确、易维护、可测试、易部署的系统，不要为了追求技术复杂度而过度设计。

### 1.2 范围边界（非目标）【补充】

以下事项**明确不属于**本项目范围，禁止为其编写代码或预留复杂抽象：

2. 不做面向终端消费者的聊天机器人产品（本项目是 ToD/ToB 的 API 基础设施）。

4. 不做多语言国际化（i18n）框架，UI 文案默认简体中文（海外模式可增加英文文案，但不做框架级 i18n），代码中不得把文案硬编码进业务逻辑。

7. 不做自有计量计费协议的发明创造；计量单位、API 协议一律对齐 OpenAI 兼容规范及上游事实。
8. 【v3.0】不做加密货币的交易、兑换、理财、staking 等任何资金增值业务；USDT 仅作为**收款手段**，到账后按记账规则入账，平台不提供提币功能（退款走人工审核原路退回，见 8.5）。

## 三、技术架构

采用清晰分层、可测试、可替换的架构。本章先给出选型结论与理由，再给出各层要求。

### 3.0 总体架构与选型结论【补充】

```text
浏览器/调用方
    │
    ▼
Nginx（TLS 终止、安全头、基础限流、静态资源）
    ├──► Next.js 前端（官网 + 控制台 + 管理后台，含 BFF 代理层）
    │        └── /api/* 由 Next Route Handler 转发到业务后端（携带 HttpOnly Cookie）
    ├──► FastAPI 业务后端（账户/权限/计费/订单/管理/审计 + OpenAI 兼容边缘 /v1/*）
    │        ├──► PostgreSQL（业务库 + 账本）
    │        ├──► Redis（限流、并发闸、短期状态、任务队列 Broker）
    │        ├──► ARQ 任务进程（邮件、对账、超时关单、链上订单确认轮询等异步作业）
    │        ├──► LiteLLM Proxy（模型路由、虚拟 Key、上游重试/回退、用量解析）
    │        │        └──► 各上游供应商 / 自建推理端点
    │        └──► 支付渠道（法币: 微信/支付宝/Stripe；加密货币: USDT 托管网关）
    └──► /v1/* 公开模型 API 流量 → FastAPI 边缘（鉴权+配额+预留）→ LiteLLM → 上游
```

**选型结论与理由（评估后确认，详见各小节与 ADR-001）：**

| 维度 | 结论 | 理由 |
| --- | --- | --- |
| 前端 | Next.js App Router + TS + Tailwind + shadcn/ui | 官网需要 SEO/SSR；Route Handler 承担 BFF |
| 业务后端 | Python 3.12 + FastAPI + SQLAlchemy 2.x（异步）+ Alembic | **经 v3.0 专项评估确认不切换 Go**：系统瓶颈在上游模型延迟（单次 10~180s）与 PostgreSQL 事务，本地 CPU 不是瓶颈；FastAPI 异步可承载数千并发 SSE 长连接；与 LiteLLM（Python）同生态便于读源码、写插件；Decimal/Pydantic 资金工具链成熟。**触发重新评估的量化条件**：单 API 节点 CPU 持续 >70%、单节点并发流 >2 万、或弃用 LiteLLM 自研网关 |
| 模型网关 | LiteLLM Proxy（独立进程，PostgreSQL 持久化） | 避免自研多供应商适配矩阵；必须核实所装版本的开源/企业版功能边界；保留自研薄网关替换可能 |
| 数据库 | PostgreSQL 16 | 账本需要强事务与精确数值 |
| 缓存/协调 | Redis 7 | 限流、并发闸、幂等暂存、任务队列 Broker；**财务状态不得以 Redis 为准** |
| 异步任务 | ARQ（Redis 队列） | 邮件、对账、超时关单、过期预扣释放、链上订单确认轮询必须移出请求生命周期 |
| 支付 | 适配器模式：法币（微信/支付宝/Stripe）+ 加密货币（USDT） | 法币与加密货币统一走支付适配器接口；USDT **一阶段强制使用托管网关**（NOWPayments / Coinbase Commerce / Binance Pay 等），不自建链节点；详见 8.5 |
| 部署 | Docker Compose（一阶段）→ 预留 K8s 路径 | 单机可复现；服务无状态化 |
| 监控 | Prometheus + Grafana（可开关）+ OpenTelemetry Trace | 起步可只开指标端点 |

**架构调整项记录（v2.0 起生效）：**

1. 业务后端数据库访问统一为**异步引擎**（asyncpg）。
2. 引入 **ARQ** 任务队列（超时关单、支付对账、邮件重试、过期预扣释放、链上确认轮询）。
3. 前端经 **BFF 代理**（Next.js Route Handler）访问业务 API。
4. 引入 **openapi-typescript**（或 hey-api）从 FastAPI 自动生成 TS 客户端。
5. 可观测性：**structlog** 结构化日志 + **OpenTelemetry**。
6. 包管理与锁定：Python 用 **uv**；Node 用 **pnpm**；提交锁文件。
7. 测试栈：pytest + pytest-asyncio + httpx（后端）、Vitest（组件）、**Playwright**（E2E）；集成测试用 docker-compose 起真实 PostgreSQL/Redis。
8. Nginx 作为反向代理与 TLS 终止（可用 Caddy 替换，需 ADR）。
9. LiteLLM：先核实版本与许可证；上游凭证只配在 LiteLLM 侧或其管理的 Secret 中（见 6.2）。

### 3.1 前端

使用：Next.js App Router（Node 22 LTS，pnpm 锁定）、React + TypeScript（strict）、Tailwind CSS、shadcn/ui 或同类成熟组件库、Zod、TanStack Query、Recharts、openapi-typescript 生成 API 客户端（禁止手写与后端不一致的请求类型）、Playwright E2E + Vitest 组件测试。

具体依赖版本应在实施时核实兼容性，使用稳定版本并锁定依赖。

前端必须适配桌面端、平板和移动端，提供统一设计规范、加载状态、错误提示、空状态、表单校验和无障碍基础支持（语义化标签、键盘可达、对比度达标）。

【补充】前端工程约束：

1. 路由守卫两层：中间件层（无 Cookie 跳登录）+ 页面数据层（401/403 统一处理）。
2. 所有金额展示以后端返回的字符串型十进制为准，前端不得用 number 累加金额；USDT 金额按 6 位小数展示，法币按 2 位。
3. 所有时间以后端 ISO8601（UTC）为准，前端按用户时区渲染。
4. 表单错误定位到字段级并支持屏幕阅读器朗读。
5. 控制台与后台表格统一封装：分页、排序、筛选、空态、加载骨架、错误重试。
6. 【v3.0】USDT 充值页必须：展示二维码 + 地址一键复制、明确标注**网络类型（TRC20/ERC20）与"错链转账不可找回"警示**、显示应付精确金额（含尾数）、实时轮询确认状态。

### 3.2 自研业务后端

使用：Python 3.12（锁定于 uv.lock）、FastAPI + Pydantic v2、SQLAlchemy 2.x（async 引擎 + asyncpg）、Alembic、PostgreSQL 16、Redis 7（异步客户端）、pytest + pytest-asyncio + httpx + coverage、Ruff + mypy（billing/payments/security/rbac 模块 strict）。

业务后端必须与模型网关分离，负责账户、权限、产品定价、计费账本、订单、后台管理和审计，禁止把所有业务逻辑写进一个 API 路由文件。

【补充】后端分层约束：

1. 目录按领域划分：`auth / users / billing / payments / providers / models / gateway / admin / audit / notifications / ops`，每领域内部分 `router → service → repository → models`；router 只做参数解析与响应组装，业务规则在 service，SQL 在 repository。
2. 所有资金与配额变更必须通过 service 层事务单元完成，禁止在 router 里直接提交事务。
3. 配置一律走 pydantic-settings；禁止散落 `os.environ` 读取。
4. 时钟一律注入（`now()` 可替换），为超时、过期、链上确认类测试提供可控时钟。
5. 提供 `make test`、`make lint`、`make migrate` 统一命令入口。

### 3.3 大模型网关

首选集成 LiteLLM Proxy 作为统一大模型转发层。官方文档：https://docs.litellm.ai/docs/

重点使用并验证：多供应商模型接入、OpenAI 兼容 API、虚拟 API Key、模型路由与负载均衡、超时/重试/故障回退、请求及 Token 用量记录、预算与速率限制、PostgreSQL 持久化、Redis 多实例限流和状态协调、管理接口与模型配置。

不得假定所有功能在所有开源版本中都可用。实现前核实当前版本、许可证、配置方式和功能限制（特别是审计日志、细粒度 RBAC、SSO 等可能属于企业版的功能），结论写入 ADR-001。

必须区分以下五类凭证，且不得混用：

1. 平台自有管理密钥（LiteLLM master key / UI 管理凭证）。
2. 上游供应商密钥（只配置在 LiteLLM 或 Secret Manager，业务后端不持久化明文）。
3. 网关内部虚拟密钥。
4. 用户使用的公开 API Key（业务后端签发与校验，见 7.1）。
5. 用户的登录会话凭证。

【补充】职责切分：公开 API Key 的签发、吊销、配额判定、费用预留由业务后端负责；LiteLLM 虚拟 Key 仅作为内部信任通道与上游用量归属手段，不直接暴露给终端用户。LiteLLM 侧限额作为第二道防线。

### 3.4 异步任务与后台作业【补充】

使用 ARQ（Redis 作为 Broker）运行独立 worker 进程。至少实现以下作业，全部具备幂等性与可重入性：

| 作业 | 触发 | 要求 |
| --- | --- | --- |
| 邮件/通知发送 | 业务事件入队 | 失败指数退避重试；最终失败记录并告警 |
| 支付订单超时关闭 | 定时扫描 | 关单不入账；关单后到账的走对账/人工流程 |
| 支付对账 | 定时 | 法币渠道按日对账；USDT 渠道按网关账单 + 订单状态比对 |
| 【v3.0】链上订单确认轮询 | 定时/事件 | 对 confirming 状态订单主动查单（网关 API），确认数达标后入账；与回调互为冗余 |
| 过期预扣释放 | 定时/启动时 | 见 8.2；释放必须幂等 |
| 调用日志归档 | 定时 | 超保留期数据转归档表/冷存储 |
| 供应商健康探测 | 定时 | 结果写回供应商健康状态 |
| 汇率快照 | 定时 | 记录来源与时间（见 8.1） |
| 【v3.0】资金归集与余额告警 | 定时 | 自托管钱包模式下监控热钱包余额，超阈值告警并提示归集（托管网关模式由网关承担） |

约束：任务载荷只传 ID 不传大对象；每个任务有超时与最大重试；worker 优雅关闭；任务失败超阈值进入死信队列并在管理后台可见。

### 3.5 基础设施

推荐：PostgreSQL（业务库与账本）、Redis（缓存/限流/协调）、Nginx（TLS/访问控制/转发）、Prometheus + Grafana（可开关）、OpenTelemetry Collector（可选）、structlog 结构化日志（JSON，含 request_id / trace_id，脱敏）、CI 自动测试与依赖安全检查（pip-audit / npm audit）。

初期采用模块化单体业务后端 + 独立 LiteLLM + ARQ worker，避免无必要的微服务拆分；网关与 worker 可独立扩容。

### 3.6 依赖锁定与环境一致性【补充】

1. Python 依赖用 uv 锁定并提交；Node 依赖用 pnpm 锁定；CI 按锁文件安装。
2. 基础镜像固定 digest 或次版本号；PostgreSQL/Redis/Nginx 版本在 compose 中显式指定。
3. `.env.example` 列出全部环境变量，按"必需/可选/生产必改"分组注释；`.env` 不入库。
4. 每次依赖升级在 IMPLEMENTATION_PROGRESS.md 记录版本与验证结果。

## 五、注册、登录和身份认证

### 5.1 注册

支持：邮箱注册；密码强度检查（≥ 10 位，含字母与数字，拒绝常见弱口令）；邮箱验证码或验证链接；验证码有效期与次数限制（默认 10 分钟、最多验证 5 次、发送间隔 ≥ 60 秒、单邮箱日发送上限）；防重复注册（邮箱唯一 + 大小写归一化）；频率限制（IP + 邮箱双维度）；用户协议与隐私政策确认（记录版本与时间）；账号状态管理（待验证/正常/冻结/注销）；可配置的邀请注册或管理员审批。

邮箱发送必须使用真实、可配置的 SMTP 服务或邮件服务商；未配置时清楚报告（健康检查标黄、注册流程明确提示），不得假装发送成功。

验证码和密码重置令牌必须安全生成（CSPRNG ≥ 128 bit），数据库只保存令牌摘要（SHA-256）。

【补充】注册记录 IP 与 UA（合规前提下）；提供邮箱变更流程（新邮箱验证通过后生效，旧邮箱收通知）。

### 5.2 登录

实现：邮箱+密码登录；登录失败限制（同账号 5 次失败锁 15 分钟，同 IP 高频升级限制）；账号冻结/解封；安全会话（服务端会话表，支持列出与踢出）；退出登录（服务端会话失效）；密码修改（校验旧密码，改后吊销其他会话并邮件通知）；密码找回；登录设备和会话管理；可选 TOTP 多因素认证（种子加密存储；一次性恢复码仅存哈希）；管理员敏感操作二次验证。

密码使用 Argon2id 哈希。优先采用服务端会话 + HttpOnly、Secure、SameSite Cookie。不得将长期登录凭证放在 localStorage。

【补充】会话细则：默认 7 天滑动过期、绝对上限 30 天；记录创建 IP/UA/最近活跃；生产 Cookie 用 `__Host-` 前缀；密码/邮箱/TOTP 变更吊销其他全部会话；CSRF 采用 SameSite=Lax + Origin 校验双保险。

【v3.0】涉及资金的操作（创建提现/退款申请、修改收款地址类敏感信息、大额人工调整）必须要求二次验证（密码或 TOTP）。

### 5.3 RBAC 权限

至少支持：普通用户、客服、财务、运营人员、模型运维人员、系统管理员、超级管理员。

服务端 RBAC，权限点粒度到 `资源:操作`。财务人员不得自动拥有供应商密钥查看权限，客服不得默认拥有退款或修改账本的权限，【v3.0】**任何单一角色不得独立完成"USDT 退款审核 + 执行"（职责分离，双人复核）**。

所有高风险操作记录审计日志。

【补充】约束：权限点清单以代码常量维护；角色/用户赋权只能走管理接口并写审计；超管仅初始化创建一个，其使用单独告警；"以该用户视角预览"功能只读、全程审计、有时限。

## 六、供应商和模型管理

### 6.1 供应商管理

支持配置：OpenAI 兼容接口；Anthropic 等不同协议服务；云厂商托管大模型服务；企业自建推理端点；Ollama 等本地推理服务；其他经验证兼容的模型 API。

每个供应商配置包括：名称和类型、基础 URL、API 协议类型、凭证引用、启用/停用状态、超时配置、连接测试、健康状态、允许访问的模型、优先级、权重、并发上限、RPM/TPM 配额、成本规则、最近错误和延迟统计。

SSRF 防护细则（必须全部实现）：

1. 仅允许 http/https；提交时解析域名并校验，拒绝私有/保留地址段（10/8、172.16/12、192.168/16、127/8、169.254/16、::1、fc00::/7、fe80::/10 等）。
2. 禁止自动跟随重定向到未校验地址（逐跳校验）。
3. 连接层固定 DNS 解析结果（防 DNS rebinding）。
4. 云元数据地址单独黑名单并告警。
5. 企业自建端点走显式白名单审批，变更写审计。

供应商密钥只能由后端使用，禁止发送给浏览器。

【补充】健康探测：可配置探测间隔（默认 60s）与方式（GET /models 免费探测默认开，最小 chat 调用默认关）；连续 N 次失败标记不可用并告警；恢复自动回切（带最少稳定时长防抖动）。

### 6.2 上游密钥管理

要求：数据库不保存明文密钥；信封加密；优先独立 KMS/Secret Manager；主密钥轮换提供重加密工具；禁止密钥进源码/Git/前端/日志；管理界面只显示掩码（前 4 后 4）；轮换/撤销写审计；生产禁止返回完整历史密钥；记录凭证引用、状态和最近使用时间。

上游密钥优先只存于 LiteLLM/Secret Manager 一处；业务库仅保存引用 ID 与元信息。若确需在业务库加密保存，使用 Fernet 或 AES-GCM 信封加密，主密钥只从环境变量/KMS 注入。

LiteLLM 自身的凭证加密密钥按其官方文档配置并单独备份，不得随意更换。

### 6.3 模型目录

每个模型具有：内部唯一 ID、对外显示名称、对外 API 模型名称、上游真实模型名称、所属供应商、能力标签、上下文窗口、最大输出限制、输入/输出计价规则、是否支持流式/工具调用/视觉/Embeddings/图像生成、是否启用、可见用户或用户组、路由策略、当前健康状态。

模型能力和限制以供应商真实资料及实际测试为准，未知字段显示"未确认"而非编造。

【补充】模型同步：对支持 GET /models 的上游提供"同步模型清单"，结果进待确认列表，运维确认能力标签与定价后方可上架；同步留痕（model_sync_jobs）。

### 6.4 模型测试

后台支持：连接测试、简单文本生成、流式输出测试、超时测试、鉴权失败测试、模型不存在测试、Token 统计检查、延迟和错误率检查。

测试不得将供应商密钥返回浏览器；测试请求内容默认不落库，只保留元数据与结果摘要（≤ 7 天）。

【补充】上架新模型或变更端点前必须通过最小测试集（连接 + 非流式 + 流式 + 用量字段校验）。

## 七、统一 API 中转层

### 7.0 端点支持矩阵【补充】

| 端点 | 第一阶段 | 说明 |
| --- | --- | --- |
| POST /v1/chat/completions | 必须 | 流式/非流式 |
| GET /v1/models | 必须 | 只返回当前 Key 有权模型 |
| POST /v1/embeddings | 必须（仅对实际支持的模型） | 无对应模型时明确报错 |
| POST /v1/images/generations | 可以 | 仅当已上架且定价完备 |
| /v1/audio/*、/v1/files、/v1/batches | 暂不开放 | 返回 501 风格明确错误 |

所有端点符合所声明的 API 协议与响应格式（对齐 OpenAI 兼容规范，含错误体结构）。

### 7.1 API Key

用户可创建多个 Key。每个 Key 包含：ID、名称、创建时间、过期时间、状态、允许使用的模型、RPM/TPM/并发限制、预算上限、可选 IP 白名单、最近使用时间。

安全要求：CSPRNG 生成（`sk-` + 32 字节 urlsafe）；数据库仅存摘要；创建时只显示一次；撤销立即生效（缓存 TTL ≤ 30s 兜底）；日志只存前缀+摘要；管理员默认不能读完整 Key；Key 仅能访问 /v1/*；严格校验用户、状态、额度、模型授权。

【补充】Key 预算上限是硬约束：预估将超出时请求前拒绝（402）。

### 7.2 请求处理流程

1. 接收请求（请求体 ≤ 4MB）→ 2. 验证 API Key → 3. 检查账户状态 → 4. 检查模型授权 → 5. 检查余额/预算/配额 → 6. 限流与并发闸（失败 429）→ 7. 确定上游与路由 → 8. 记录 request_id → 9. 费用预留（预扣）→ 10. 调用 LiteLLM → 11. 处理普通/流式响应 → 12. 收集上游用量（无则按估算打标）→ 13. 计算实际费用 → 14. 结算（预扣转实扣，多退少补）或失败释放 → 15. 写调用记录与账本 → 16. 释放槽位，返回规范化响应。

必须考虑客户端中断、超时、重试、上游错误、流式中断和进程崩溃。

【补充】可靠性细则：预扣带 TTL（默认 10 分钟），崩溃由后台作业回收；并发槽位带租约；调用记录"先 pending 后 finalize"两阶段写入；鉴权后的失败路径也落记录，供对账与风控。

### 7.3 流式响应

正确支持 SSE：不缓冲完整响应；逐段转发；正确 Content-Type（text/event-stream）；客户端断开时取消上游；处理上游超时；finally 归还槽位；记录首 Token 延迟、总耗时、最终状态；兼容客户端取消；不向用户暴露内部堆栈。

不得因流式导致费用漏记、重复扣费或无限占用并发。

【补充】流式计费一致性：上游支持 `stream_options.include_usage` 时必须启用；流结束未取得用量时用本地 tokenizer 估算并打标 `usage_source=estimated`；流中断按已产生用量结算并标注 finish_reason。

### 7.4 故障回退

支持：同模型不同供应商备用端点、故障切换、超时重试、熔断与恢复探测、权重路由、限流感知路由。

不得无条件重试。只有协议兼容、授权明确且能力匹配的模型才允许作为自动回退目标。

【补充】重试矩阵（默认值，可配置）：

| 失败类型 | 是否重试 | 说明 |
| --- | --- | --- |
| 连接失败/连接超时（未发出请求体） | ≤ 2 次，换端点 | 幂等安全 |
| 读超时（已发出，未收到字节） | 同供应商 ≤ 1 次 | 记录"可能产生上游费用"标记 |
| 上游 429 | 换端点 ≤ 1 次 | 限流感知 |
| 上游 5xx | 换端点 ≤ 1 次 | 熔断期内跳过故障端点 |
| 上游 4xx | 不重试 | 透传规范化错误 |
| 流式已开始后中断 | 不重试 | 按已产生用量结算 |

## 八、定价、余额与计费系统

这是商业化系统的重点，必须认真实现。

### 8.1 定价体系

价格规则至少包含：输入/输出 Token 单价、缓存输入单价（适用时）、图片或其他计量单位价格（适用时）、最低计费单位、计费币种、生效/失效时间、价格版本、供应商成本、用户销售价格。

必须区分供应商成本和用户售价。调价不得静默修改历史订单/账单；每次调用保存定价版本或结算快照。明确区分币种，禁止不同币种金额直接相加；汇率换算记录来源、时间和规则。

【补充】细则：

1. 站内账本单一结算币种（大陆模式 CNY，海外模式 USD；USDT 按 8.5 规则折算 USD 入账）。
2. 价格表"版本 + 生效区间"设计，调价即新增版本；用量记录冗余保存单价快照。
3. 管理后台提供"调价预览"。

### 8.2 余额与账本

追加式账本。流水类型：充值入账、模型调用扣费、退款、人工调整、优惠/补偿、预扣/释放、冻结、对账差异调整（全量类型见附录 B）。

关键要求：PostgreSQL 事务；金额用 NUMERIC，禁止浮点；唯一业务流水号 + 幂等键；防并发重复扣款；防余额不足继续消费；原子额度预留（三段式 hold → commit → release）；记录变更前后金额与原因；普通管理员不得修改历史账本（只能新增冲正流水）；退款必须引用原始订单/流水；异常与延迟用量设待结算状态。

账本不变量（必须写成测试断言与对账 SQL）：

1. `余额 = Σ已提交流水`；`可用余额 = 余额 - 生效中预扣 - 冻结金额`。
2. 每条预扣最终必须且只能走向 commit 或 release 之一。
3. 账本只增不改，纠错走反向流水。
4. 幂等键全局唯一，同键重放返回首次结果。
5. 余额行用 `SELECT ... FOR UPDATE` 或条件更新（`UPDATE ... WHERE balance >= ?`）保证并发安全。

### 8.3 调用计费

优先使用上游实际返回用量；无返回时才用估算并打标（`usage_source: reported | estimated`）。

每条调用记录至少包括：request_id、用户 ID、API Key ID、模型 ID、上游部署 ID、开始时间、首 Token 时间（适用时）、结束时间、输入/输出/缓存 Token、供应商成本、用户费用、币种、定价版本、HTTP 状态、错误类别、是否流式、结算状态。

不默认保存完整提示词与返回内容；内容留存须显式配置、权限控制并设保留期。

【补充】结算状态机：`pending → settled | released | disputed`；disputed 由对账作业或人工处理，全程留痕。

### 8.4 充值和支付（通用要求 + 法币渠道）

支付适配器接口，支持接入合法支付服务商。包括：充值套餐、充值订单、支付创建、状态查询、回调验签、回调幂等、超时关单、退款流程、订单对账、财务操作日志。

适配器最小契约：`create_payment / query_payment / verify_notification / refund / query_refund / reconcile(bill_date)`。

开发环境提供明确标记的模拟支付适配器；`APP_ENV=production` 且启用 mock 时进程必须拒绝启动。不得仅凭前端传参加余额；支付成功必须服务端可信验证（验签 + 主动查单），同一订单最多入账一次。所有支付事件原文（脱敏）落 `payment_events` 表，处理可重放审计。退款默认原路退回，审批流（发起 → 财务复核 → 执行）。

法币渠道：大陆模式接微信支付/支付宝（需营业执照与商户号，开发期用 mock）；海外模式接 Stripe（Checkout Session + Webhook 验签）。涉及实际支付前必须核实服务商要求、税务与法律合规。

### 8.5 USDT（加密货币）收款专节【v3.0】

> 仅海外模式启用；启用前运营方必须完成第十九章的合规评估。以下全部为强制性设计要求。

#### 8.5.1 渠道选型（一阶段结论：托管网关）

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 托管支付网关（NOWPayments / Coinbase Commerce / Binance Pay 等） | **一阶段采用** | 无需自建节点；网关承担地址分配、确认监控、回调签名；运营门槛低 |
| 自托管 BTCPay Server 或自研链上扫描 | 二阶段可选 | 需维护节点/扫描器与私钥，安全成本高；切换时以适配器模式平移，不影响业务代码 |
| 直接给用户一个固定收款地址人工核对 | **禁止** | 无法区分订单、无法幂等、对账灾难 |

选择网关时的硬性评估项：支持 TRC20-USDT；回调 HMAC 验签；支持主动查单 API；支持订单独立收款地址或金额尾数区分；手续费结构透明；有制裁地址筛查能力者优先。评估结论写 ADR。

#### 8.5.2 订单与金额规则

1. 订单币种 USD，链上收款币种 USDT；下单时锁定换算数量（USDT≈USD，记录锁价时刻与来源），订单有效期默认 30 分钟。
2. **并发订单必须可区分**：优先由网关为每单分配独立收款地址；网关只支持固定地址时，采用金额尾数扰动（如在 0.0001~0.0099 USDT 区间分配唯一尾数，尾数池带锁分配、过期回收）。
3. 明确展示：收款地址、网络（TRC20 默认；ERC20 可配，提示矿工费高）、精确应付金额、二维码、"错链/错币转账不可找回"警示。
4. 最低充值金额可配（默认 ≥ 5 USDT），页面提示链上手续费与网关手续费由谁承担。

#### 8.5.3 确认与入账（防双花/防重组）

1. 订单状态机：`pending → confirming → completed | expired | underpaid | overpaid | closed →（可）refunded`。
2. **确认数分档**（默认，可配）：< 100 USD 等值 ≥ 1 个区块确认；100~1000 USD ≥ 2；> 1000 USD ≥ 3 并触发人工复核提示。TRC20 按 Tron 出块计；ERC20 按 Ethereum 确认数计。
3. **入账三重验证**（缺一不可）：网关回调 HMAC 验签通过 + 回调源 IP 白名单 + 服务端主动调网关查单 API 核对金额/地址/确认数一致。
4. 回调与确认轮询作业互为冗余；两者都必须幂等（`crypto_confirm:{order_no}` 幂等键），同一订单最多入账一次。
5. 金额偏差处理：少付（underpaid）不自动入账，用户可补足或申请按实付入账（需配置允许）；多付（overpaid）按实付入账并在订单标记，多出部分可人工退款；错链/错币转账平台不自动入账，走人工工单，手续费规则在服务条款公示。
6. 链上交易哈希、确认数、实际到账金额、锁价全部落库（payment_orders + payment_events），对账作业按日核对网关账单与本地流水。

#### 8.5.4 资金安全

1. 一阶段资金沉淀在托管网关，平台**不持有用户充值私钥**；按网关结算周期提现至运营方受控钱包。
2. 若启用自托管钱包（二阶段）：冷热分离（热钱包仅留运营下限金额，阈值告警自动提示归集）；私钥使用 KMS/HSM 或离线签名，**禁止明文私钥出现在服务器磁盘、环境变量、数据库、日志**；提币双人复核 + 二次验证 + 白名单地址。
3. USDT 退款：平台无提币功能；退款由财务在后台发起 → 复核 → 在网关/钱包侧手动执行，系统记录审批链与交易哈希；退款只能退回**原付款地址**（地址由链上记录佐证，禁止退到用户口头提供的新地址，防洗钱）。
4. 管理后台"加密资产台账"只读展示汇总，不接触私钥。

#### 8.5.5 加密货币专项风控

1. 制裁/黑名单地址筛查：命中 OFAC SDN 等黑名单来源地址的充值**冻结入账**并人工审核（网关自带能力或配置地址黑名单表）。
2. 单用户 USDT 充值频率与日累计限额可配；异常模式（多账号同地址付款、短时高频小额）触发风控告警。
3. 回调接口独立限流与告警；验签失败出现即告警（可能是伪造攻击探测）。
4. 汇率操纵防护：锁价来自可信行情源（多源取中位），偏差超阈值拒绝下单。

## 十二、API 规范

- RESTful；业务 API 前缀 /api/v1；公开模型 API 前缀 /v1（OpenAI 兼容）。
- 统一响应结构（业务：`{ ok, data, error, request_id }`）。
- 统一错误码（附录 A）。
- 参数校验（Pydantic/Zod 双层）。
- 分页：page/page_size（默认 1/20，≤ 100）含 total；导出类提供 cursor 分页。
- 排序/过滤：sort=field,-field2；过滤参数白名单化，禁止字段名注入。
- 请求关联 ID（响应头 + 响应体 X-Request-Id）。
- 幂等键：所有创建类 POST 接受 Idempotency-Key；同键重放返回首次结果（含状态码），保留 24 小时。
- 版本控制：破坏性变更升 /api/v2；旧版维护 ≥ 6 个月并公告。
- OpenAPI 文档自动生成（生产需鉴权或内网可见）；契约测试入 CI。
- 错误响应不泄露内部实现；5xx 只返回通用文案 + request_id。

覆盖：认证、用户、模型目录、API Key、供应商、部署、用量、账单、充值（含 USDT）、订单、通知、工单、发票、管理、审计。管理接口与公开模型 API 分离；服务端所有查询强制归属条件防 IDOR。

## 十四、安全审计清单

至少检查：SQL 注入、XSS、CSRF、SSRF、IDOR、弱密码/暴力破解、会话固定/劫持、API Key 泄露、上游密钥泄露、账单篡改、并发重复扣费、充值回调重放、管理接口未授权、请求体过大、恶意流式请求、无限并发、请求风暴、过度重试、敏感信息写日志、依赖漏洞、默认密码/调试接口暴露、数据库和 Redis 暴露公网、CORS 过宽、反代信任配置错误、备份中的密钥和个人数据保护。

【v3.0】加密货币专项威胁清单：

1. 回调伪造 → HMAC 验签 + IP 白名单 + 主动查单三重验证（8.5.3）。
2. 链上重组/双花 → 确认数分档 + 确认轮询冗余 + 大额人工复核。
3. 地址投毒（攻击者用相似地址污染用户剪贴板/历史记录）→ 充值页每次生成动态地址并二维码展示；订单页展示地址首尾各 8 位供核对；禁止复用历史订单地址。
4. 并发订单金额碰撞 → 独立地址或尾数池带锁分配（8.5.2）。
5. 错链/错币/少额多转 → 不自动入账 + 人工流程 + 费率公示。
6. 私钥泄露/热钱包被盗 → 一阶段托管网关不持私钥；自托管冷热分离 + 白名单提币 + 双人复核。
7. 洗钱风险（平台被用作资金通道）→ 退款只回原地址；制裁地址筛查；充值频率/累计限额；不提供提币功能。
8. 汇率锁价操纵 → 多源中位行情 + 偏差拒绝。

使用适当安全测试工具与人工审查；不得把"通过扫描"等同于绝对安全。

【补充】STRIDE 威胁模型（阶段 8 逐项核验并写入 SECURITY.md）：仿冒（会话劫持/Key 泄露）、篡改（账本篡改/回调伪造）、抵赖（管理员操作）、信息泄露（密钥/提示词）、拒绝服务（请求风暴/恶意长连接）、提权（IDOR/越权）。

安全测试落地：CI 跑 Bandit/pip-audit/npm audit；阶段 8 跑 OWASP ZAP Baseline；鉴权、IDOR、并发扣费、回调重放、加密回调伪造编写负向测试用例（TC-SEC-*），全部通过才可验收。

## 十九、合规与内容安全【补充】

> 本章为默认基线，具体适用性由运营方根据经营地区与业务实质咨询法务确认；实施时不得删除本章要求，不适用项需书面说明理由。

### 19.1 大陆模式

1. ICP 备案/许可评估；经营性收费评估 ICP/EDI；官网页脚预留备案号位。
2. 生成式 AI 服务相关备案/登记义务评估。
3. 内容安全：可配置审核钩子（入参/出参两个挂点，默认关闭接口就位）；命中记录进 content_audit_records（默认只存类别与摘要哈希）；支持按模型/用户组强制启用。
4. 日志留存按适用法规定保留期（默认矩阵见第九章，合规更长时以合规为准）；到期自动清理作业。
5. 个人信息保护：协议确认记录；账号注销（法定留存数据除外并明示）；个人信息副本导出。
6. 数据出境：上游涉境外服务时官网明示；企业客户支持"仅境内上游"分组。
7. 税务与发票：收费前确认纳税与开票义务；发票模块记录抬头/税号/金额/状态。
8. 未成年人保护：服务条款明确年龄要求。

### 19.2 海外模式【v3.0】

1. **加密货币红线**：USDT 收款必须由海外主体运营，**禁止向中国大陆居民提供虚拟货币兑换、交易、充值服务**；用户协议声明服务地区限制；必要时按 IP/注册信息做地区筛查。
2. 制裁合规：对受制裁国家/地区（按运营主体适用法域，如 OFAC 清单）做用户与来源地址筛查；命中冻结入账并人工审核（见 8.5.5）。
3. KYC/AML：平台默认低门槛邮箱注册，但**累计充值或退款超过可配阈值时触发增强审核**（工单通道要求补充信息）；保留交易记录 ≥ 5 年。
4. GDPR（如有欧盟用户）：数据删除权、处理记录、DPO 需求评估；隐私政策覆盖。
5. 税务：加密货币收入按运营主体所在地规则记账申报；账本中 USDT 按锁价折算 USD 入账即为此服务。
6. 机房与数据处理地：海外机房部署；隐私政策明示数据存储地。
