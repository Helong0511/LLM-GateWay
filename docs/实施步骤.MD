# 实施步骤（九阶段详细执行手册）

> 配套：《软件需求.MD》v3.0（需求，章节号 §N 均指该文档）、《实施守则.MD》（纪律）。
> 用法：按阶段顺序执行；每步完成后立即验证并更新 `IMPLEMENTATION_PROGRESS.md`；每阶段末尾核对 DoD。
> 环境前提：Ubuntu 22.04.5（或 Windows + WSL2 开发），已装 Docker + Docker Compose、Node 22 + pnpm、Python 3.12 + uv、Git。

## 目录结构约定（阶段 2 创建，全程沿用）

```text
/
├── apps/
│   ├── api/            # FastAPI 业务后端（pyproject.toml + uv.lock）
│   └── web/            # Next.js 前端（pnpm-lock.yaml）
├── deploy/
│   ├── docker-compose.yml          # 开发环境（含 mailpit、mock）
│   ├── docker-compose.staging.yml
│   ├── docker-compose.prod.yml     # 不含密钥，密钥走 env_file
│   └── nginx/                      # nginx.conf + TLS 示例
├── docs/               # 全部工程文档 + adr/
├── scripts/            # init_admin.sh、backup.sh、restore.sh、smoke.sh
├── sql/                # 手工 SQL（对账、归档），迁移一律走 Alembic
└── tests/              # 跨层集成/并发/E2E 测试
```

## 阶段 1：审计与架构确认

**步骤**
1. 盘点工作区：列出现有全部文件；已有代码逐模块给出"保留/修复/重构/替换"结论（守则 §2.1-2）。
2. 核实 LiteLLM 当前稳定版本、开源版/企业版功能边界（重点：虚拟 Key、预算、限流、审计），结论写 `docs/adr/ADR-001-litellm-选型.md`。
3. 选定金流模式：大陆模式 or 海外模式（USDT）；写 `docs/adr/ADR-002-运营模式.md`。
4. 编写 `docs/PROJECT_AUDIT.md`（现状与风险清单）、`docs/ARCHITECTURE.md`（按需求 §3.0 架构图展开）、`docs/DATABASE_DESIGN.md`（草图：需求 §9 全部实体的字段与关系）。
5. 把需求 §18 验收矩阵逐条拆成任务清单，录入 `IMPLEMENTATION_PROGRESS.md`。

**验证**：四份文档落盘；ADR 两份；任务清单可追踪到章节号。
**DoD**：需求 §17 阶段 1 全部条目 ✅。

## 阶段 2：基础工程

**步骤**
1. 建目录结构（如上）；写 `.gitignore`（.env、node_modules、__pycache__、.data）、`.env.example`（分组注释）。
2. `deploy/docker-compose.yml`：postgres:16、redis:7、mailpit（开发收信）、litellm（先空配置占位）。全部显式版本号、健康检查、资源限制。
3. 后端骨架（apps/api）：`uv init` → 依赖按需求 §3.2 → 实现 app 工厂、配置（pydantic-settings）、structlog 日志 + 脱敏过滤器、统一错误处理（需求 §12 响应结构 + 附录 A 错误码）、/healthz、/readyz（含 PG/Redis 检查）、request_id 中间件。
4. Alembic 初始化；第一批迁移：users、roles、permissions、user_roles、sessions、email_verification_tokens、password_reset_tokens。
5. ARQ worker 骨架：独立进程入口、一个示例任务、优雅关闭。
6. 前端骨架（apps/web）：`create-next-app`（App Router + TS strict + Tailwind）→ shadcn/ui 初始化 → BFF 代理 Route Handler（/api/* 转发到后端，转发 Cookie）→ openapi-typescript 代码生成脚本。
7. CI（GitHub Actions 或等价）：后端 ruff + mypy + pytest；前端 lint + vitest + build；pip-audit/npm audit。
8. 写 `scripts/init_admin.sh`（生成一次性超管初始化令牌，只打印一次）。

**验证**：`docker compose up -d && curl localhost:8000/healthz` 返回 ok；`readyz` 含依赖检查；CI 绿；浏览器打开前端能看到骨架页。
**DoD**：需求 §17 阶段 2 全部 ✅。

## 阶段 3：官网与认证

**步骤**
1. 官网 18+1 个页面（需求 §4.1），演示数据全部带"演示"水印标记；/status 接健康检查真实数据。
2. 认证后端：注册（邮箱验证码：CSPRNG 令牌 + 仅存 SHA-256 摘要 + 有效期/次数/频率限制）、Argon2id 密码哈希、登录（失败锁定）、服务端会话（HttpOnly+Secure+SameSite Cookie，7 天滑动/30 天上限）、登出、密码找回/修改、邮箱验证、邮箱变更。
3. RBAC 基座：七种角色种子数据、权限点常量、服务端校验装饰器、用户-角色赋权接口。
4. 邮件：SMTP 适配器（未配置时明确报"未配置"，不假装成功）；开发环境用 mailpit 收信。
5. 前端页面：注册/登录/忘记密码/重置密码/邮箱验证 + 路由守卫（中间件 + 401/403 统一处理）。
6. TOTP（可选但本期实现）：种子加密存储、恢复码存哈希、二次验证接口。

**验证**：TC-AUTH-001~011、TC-RBAC-001~ 全部实际执行通过；未登录访问 /console 跳登录；普通用户访问 /admin 403；日志中无密码/令牌明文（人工抽查 + 脱敏测试）。
**DoD**：需求 §17 阶段 3 ✅。

## 阶段 4：用户控制台

**步骤**
1. API Key 管理：创建（CSPRNG `sk-`+32B，只存摘要，只展示一次）、列表（掩码）、吊销（立即生效 + 缓存 ≤30s 兜底）、模型授权、RPM/TPM/并发/预算/IP 白名单字段。
2. 用量统计与请求记录：usage_records 写入链路（先 pending 后 finalize）、按用户隔离的查询接口（分页/筛选/排序）。
3. 仪表盘：需求 §4.2 顶部全部指标（真实接口，标口径与时区）+ Recharts 趋势图。
4. 账单页：账本流水查询（只读）、余额展示（字符串十进制）。
5. 通知中心：站内通知表 + 列表/已读接口；余额预警触发器（阈值可配）。
6. 个人资料 + 安全设置（会话/设备管理、改密、TOTP 绑定）。

**验证**：TC-KEY-001~ 通过（含"创建只展示一次"、"吊销立即生效"）；仪表盘每个数字可追溯到 SQL；TC-FE-* 表格分页/空态/错误态通过。
**DoD**：需求 §17 阶段 4 ✅。

## 阶段 5：LiteLLM 网关集成

**步骤**
1. compose 中起 LiteLLM（PostgreSQL 持久化 + master key 走 env_file；管理接口仅内网）；按 ADR-001 结论配置。
2. 供应商管理模块：providers/provider_credentials CRUD（密钥掩码、只存 LiteLLM 侧或信封加密）；SSRF 五条校验（需求 §6.1）全部实现 + 单测。
3. 模型目录：model_catalog/model_deployments 建模；从上游同步模型清单 → 待确认 → 上架流程。
4. /v1/chat/completions、/v1/models、/v1/embeddings 边缘层：鉴权 → 账户状态 → 模型授权 → 预算检查 → 限流/并发闸 → 转发 LiteLLM → 规范化响应（OpenAI 兼容错误体）。
5. SSE 流式转发：逐段推送、客户端断开取消上游、finally 释放槽位、首 Token 延迟记录、`stream_options.include_usage`。
6. 模型测试工具（后台）：连接/生成/流式/超时/鉴权失败/模型不存在/用量校验。
7. Mock 供应商（OpenAI 兼容假上游，可控错误/延迟/用量）供自动化测试。

**验证**：TC-GW-* 通过（Mock 上游）；流式中断费用与槽位正确；SSRF 负向用例通过；密钥不出现在任何响应与日志（grep 测试）。
**DoD**：需求 §17 阶段 5 ✅。

## 阶段 6：计费系统（资金红线区，守则 §四）

**步骤**
1. 价格体系：model_prices + pricing_versions（版本+生效区间）；单价快照随用量记录落库。
2. 账本：account_balances + account_ledger + balance_holds；三段式预扣（hold→commit/release）；五条不变量写成测试断言 + 对账 SQL。
3. 请求路径接入预扣（需求 §7.2 第 9 步）；流式/中断/超时各终态的结算或释放；过期预扣回收作业。
4. 充值：recharge_products、payment_orders、payment_events；适配器接口（6 个方法，需求 §8.4）；mock 适配器（production 拒绝启动）。
5. 法币渠道：按 ADR-002 选 Stripe（海外，Webhook 验签）或微信/支付宝（大陆）；验签 + 主动查单 + 幂等入账。
6. USDT 渠道（海外模式）：网关适配器；尾数池/独立地址；确认数分档；三重验证；回调+轮询冗余幂等；少付/多付/错链处理流程（需求 §8.5 全节）。
7. 对账作业：法币按日对渠道账单；USDT 对网关账单；差异入 disputed + 告警。
8. 超时关单作业、支付管理后台视图。

**验证**：TC-BILL-*、TC-PAY-*（含 TC-PAY-101~ USDT 组）、TC-CONC-*（并发竞争额度账目守恒、回调并发只入账一次）全部通过；mock 生产拒绝启动有测试。
**DoD**：需求 §17 阶段 6 ✅。

## 阶段 7：管理后台

**步骤**
1. 独立 /admin 布局与权限门；后台全部 26 个模块（需求 §4.3）按优先级：运营概览 → 用户 → 角色权限 → 供应商/凭证 → 模型/部署/路由 → 价格 → 订单支付 → 余额账本 → 调用记录 → 限流配额 → 审计 → 系统配置 → 公告/工单/发票/对账毛利/台账/任务监控。
2. 审计日志：哈希链（prev_hash）+ 校验接口 + 定期校验作业。
3. 高风险操作：二次确认 + 二次验证 + 审计三件套（供应商密钥、模型上下架、调价、封禁、Key 吊销、退款、账本调整、权限变更、USDT 人工入账/退款）。
4. USDT 退款双人复核流（发起/执行分离）。
5. 后台负向权限测试：每个模块验证越权角色访问被拒。

**验证**：TC-ADMIN-* 通过；审计链校验通过；权限矩阵负向用例全过。
**DoD**：需求 §17 阶段 7 ✅。

## 阶段 8：安全与性能

**步骤**
1. STRIDE 逐项核验 + 加密货币专项清单（需求 §14）逐项给证据，写 SECURITY.md。
2. 负向安全用例 TC-SEC-*：IDOR、越权、伪造回调（法币+USDT）、重放、SSRF、日志泄露 grep。
3. 故障注入：Redis 断（降级行为符合 fail_mode）、PG 断（就绪 503）、LiteLLM 断（规范化错误）、流式中断。
4. OWASP ZAP Baseline；Bandit；依赖审计清零高危。
5. k6/locust 压测：业务 API 与 /v1 转发链路；校准 SLO（需求 §13 表）；容量规划三档写入 DEPLOYMENT.md。
6. RUNBOOK.md 补齐需求 §15 列出的全部故障场景处置。

**验证**：TC-SEC-* 全过；ZAP 无高危；压测报告落盘；SLO 实测值记录。
**DoD**：需求 §17 阶段 8 ✅。
