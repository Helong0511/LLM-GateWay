# ADR-001：LiteLLM 选型与版本锁定

- 状态：已接受
- 日期：2026-10-28
- 背景与问题：

业务后端需要把多家上游模型统一成 OpenAI 兼容接口。自研多供应商适配矩阵成本高，且容易在流式、用量字段和故障回退上出错。需求 §3.3 要求先核实当前版本的开源版与企业版边界，再决定哪些能力放在 LiteLLM，哪些留在业务后端。

- 备选方案（含不做的理由）：

1. 自研网关。可控，但第一阶段要把 OpenAI、Anthropic 以及各家兼容接口的差异、重试和用量解析都做一遍，偏离“不要为复杂度而设计”。
2. 只在业务后端里直接请求上游。少一个进程，但供应商差异会渗进计费代码，后续替换成本更高。
3. LiteLLM Proxy 独立进程。开源网关已经覆盖虚拟 Key、预算、限流、路由和 PostgreSQL 持久化。企业版能力不作为第一阶段前置。

- 决策：

锁定 **LiteLLM v1.106.5**（2026-10-27 发布，镜像 `ghcr.io/berriai/litellm:v1.106.5`，Python 包 `litellm==1.106.5`）。许可证为 MIT，可自托管。

开源版纳入本项目的能力：虚拟 Key、预算与速率限制、用量与花费跟踪、负载均衡与回退、OpenAI 兼容代理、PostgreSQL 持久化、Prometheus 指标。这些只作为第二道防线。

明确不依赖企业版：SSO/SCIM、LiteLLM 审计日志、组织级 RBAC、Secret Manager 集成、IP 允许列表、多区域控制面。审计、权限、用户 API Key 和资金账本全部由业务后端实现。上游凭证只配置在 LiteLLM 或后续 Secret Manager，业务库不保存明文。

重新评估条件沿用需求 §3.0：单 API 节点 CPU 持续高于 70%、单节点并发流超过 2 万，或决定弃用 LiteLLM 自研网关。

- 影响与后果（正面/负面）：

正面：供应商适配和流式转发有现成实现，业务后端可以集中做鉴权、预扣和账本。负面：多一个进程和一套数据库；企业版审计不能当作平台审计；空的 `model_list` 只能证明进程可配置，不能证明已经接通上游。

- 验证方式：

版本与功能边界对照官方发布说明（v1.106.5）和企业版功能页。本机没有 Docker，镜像尚未实际拉取。阶段 5 用 Mock 供应商跑 TC-GW-*，不把文档核对当成调用成功。
